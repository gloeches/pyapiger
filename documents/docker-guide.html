Guide: Running Your flask-api.py in a Docker Container

This document provides a step-by-step guide on how to containerize your flask-api.py application using Docker. This approach ensures your application runs in a consistent and isolated environment, making it easily portable.

A Note on Virtual Environments (like virtualenv)

You mentioned using pip virtualenv. In a typical Docker workflow, you do not need to create a virtual environment inside the container. The Docker container itself acts as the isolated environment. The Dockerfile will define the Python environment and its dependencies directly.

Prerequisites

  • Docker Desktop installed and running on your machine.

Step 1: Organize Your Project

It's best practice to have all your application files in a single project directory. 

my-flask-app/
├── Dockerfile
├── config_generator.py
├── entrypoint.sh
├── flask-api.py
└── requirements.txt

Step 2: Review the Application Components

The Flask API (flask-api.py)

This is your core Python application that serves the API. It reads its configuration from a config.json file.

The Requirements File (requirements.txt)

This file lists the Python packages your application needs.

requirements.txt 
Flask
flask-cors

The Configuration Generator (config_generator.py)

This Python script dynamically generates the config.json file when the container starts. It reads environment variables to create the configuration.

config_generator.py 
import os
import json

def generate_config():
    production_env = os.environ.get("PRODUCTION", "false").lower() == "true"
    api_port = os.environ.get("API_PORT", 5000)
    
    if production_env:
        config_data = {"DDBB-SERVER": "PRODUCTION", "API-PORT": api_port}
    else:
        config_data = {"DDBB-SERVER": "DEVELOPMENT", "API-PORT": api_port}
        
    with open("config.json", "w") as config_file:
        json.dump(config_data, config_file, indent=4)
    print(f"El puerto es {api_port}")    
    print(f"la compilación:  {production_env}")   
if __name__ == "__main__":
    print("Generating configuration file...")
    generate_config()

This script allows you to change the app's behavior at runtime by passing environment variables (PRODUCTION and API_PORT) to the `docker run` command.

The Entrypoint Script (entrypoint.sh)

This shell script is the first thing that runs when the container starts. Its job is to prepare the environment and then run the main application.

entrypoint.sh 
#!/bin/sh
# entrypoint.sh

# Run the config generator
python config_generator.py

# Now, execute the command passed to this script (the Dockerfile's CMD)
exec "$@"

The exec "$@" part is important. It replaces the shell process with the command passed as arguments, which in our case will be python flask-api.py. This ensures that the Python application becomes the main process of the container.

Step 3: Create the Dockerfile

The Dockerfile brings all these components together to build your container image.

Dockerfile 
# Use an official Python 3.13 runtime as a parent image
FROM python:3.13-slim

# Set the working directory inside the container
WORKDIR /app

# Add a build-time argument for the port
ARG port=5000

# Copy the requirements file into the container at /app
COPY requirements.txt .

# Install any needed packages specified in requirements.txt
RUN pip install --no-cache-dir -r requirements.txt
RUN pip install --upgrade pip

# Copy the rest of the application code into the container at /app
COPY . .

# Make the entrypoint script executable
RUN chmod +x entrypoint.sh

# Make port available to the world outside this container
EXPOSE $port

# Set the entrypoint
ENTRYPOINT ["./entrypoint.sh"]

# Define the command to run your app
CMD ["python", "flask-api.py"]

Explanation of the Dockerfile (Option 1):

  • FROM python:3.13-slim: Specifies a lightweight Python 3.13 base image.
  • WORKDIR /app: Sets the default directory for subsequent commands to /app.
  • ARG port=5000: Defines a build-time variable for the port. This is used by the `EXPOSE` instruction.
  • COPY requirements.txt . and RUN pip install ...: Copies the requirements file and installs the Python dependencies.
  • COPY . .: Copies all your application files (flask-api.py, config_generator.py, entrypoint.sh, etc.) into the container.
  • RUN chmod +x entrypoint.sh: Makes the entrypoint script executable so it can be run.
  • EXPOSE $port: Informs Docker that the container will listen on the specified port at runtime.
  • ENTRYPOINT ["./entrypoint.sh"]: This is the key instruction. It configures the container to run the entrypoint.sh script as its main process.
  • CMD ["python", "flask-api.py"]: This provides the default command to the ENTRYPOINT. The entrypoint.sh script will execute this command using exec "$@" after it has finished its own tasks (like generating the config).

Step 4: Build the Docker Image

Open a terminal, navigate to your project directory, and run the build command: 

docker build -t my-flask-api .

Step 5: Run the Docker Container

Now you can run the container. Since the application is configured by environment variables, you can easily change its behavior.

Running in Development Mode

This command runs the container, mapping your local port 5000 to the container's port 5000.

docker run -d -p 5000:5000 --name my-api-dev my-flask-api

Running in Production Mode on a Different Port

Here, we pass environment variables using the -e flag to run in production mode and change the port to 8080.

docker run -d -p 8080:8080 -e API_PORT=8080 -e PRODUCTION=true --name my-api-prod my-flask-api
  • -p 8080:8080: Maps port 8080 on your host to port 8080 in the container.
  • -e API_PORT=8080: Sets the API_PORT environment variable inside the container. The config_generator.py will use this to set the port in config.json.
  • -e PRODUCTION=true: Sets the PRODUCTION environment variable to `true`, causing the config generator to set the `DDBB-SERVER` to "PRODUCTION".

Step 6: Verify It's Running

You can access your containerized API in a web browser. If you ran in production mode on port 8080, the URLs would be:

  • API Landing Page: http://localhost:8080/
  • Sample API Request: http://localhost:8080/api?value=10

Anexo: Adding a Health Check (for Option 1)

To make your container more robust, you can add a HEALTHCHECK instruction to your Dockerfile. This allows Docker to periodically check if your application is still healthy.

Here is how you would modify the Option 1 Dockerfile to include a health check:

Dockerfile (with Health Check) 
# Use an official Python 3.13 runtime as a parent image
FROM python:3.13-slim

# Set the working directory inside the container
WORKDIR /app

# Copy the requirements file into the container at /app
COPY requirements.txt .

# Install any needed packages specified in requirements.txt
RUN pip install --no-cache-dir -r requirements.txt
RUN pip install --upgrade pip

# Install curl for the healthcheck
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

# Copy the rest of the application code into the container at /app
COPY . .

# Make the entrypoint script executable
RUN chmod +x entrypoint.sh

# Make port available to the world outside this container
EXPOSE 5000

# Add a health check
HEALTHCHECK --interval=30s --timeout=30s --start-period=5s --retries=3 \
  CMD curl -f http://localhost:${API_PORT}/ || exit 1

# Set the entrypoint
ENTRYPOINT ["./entrypoint.sh"]

# Define the command to run your app
CMD ["python", "flask-api.py"]

Explanation of the Changes:

  • Installing curl: 
    RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

    We add this line to install the curl command-line tool, which the health check uses to send a request to the web server.

  • The HEALTHCHECK Instruction: 
    HEALTHCHECK --interval=30s --timeout=30s --start-period=5s --retries=3 
  CMD curl -f http://localhost:${API_PORT}/ || exit 1

    This command tells Docker to run curl -f http://localhost:${port}/ || exit 1 every 30 seconds to check if the application is responding correctly. Let's break it down:

    • curl -f http://localhost:${API_PORT}/: It uses the curl tool to make an HTTP request to your application running on localhost inside the container. Crucially, it uses the API_PORT environment variable to determine which port to probe. This allows you to dynamically set the application's port during docker run using the -e API_PORT=<your_port> flag. The -f (or --fail) flag is important: it tells curl to return a non-zero exit code if the server responds with an HTTP error code (like 404 or 500), but to not print the response body.
    • || exit 1: This is a shell "OR" operator. It means: "If the command on the left (curl) fails (returns a non-zero exit code), then execute the command on the right (exit 1)."

    Why exit 1?

    Docker's health check mechanism relies on the exit code of the command:

    • Exit Code 0: Success. The container is considered "healthy".
    • Exit Code 1 (or any non-zero): Failure. The container is considered "unhealthy".

    When your application is running correctly, curl -f will get a successful response (like HTTP 200 OK), and it will exit with code 0. The || exit 1 part is ignored, and Docker sees the "healthy" signal.

    If your application has crashed or is returning an error, curl -f will fail and exit with a non-zero code (e.g., 22 for a 404 error). The shell sees this failure, and the || operator triggers the exit 1 command. This ensures that Docker receives a clear "unhealthy" signal (exit code 1). After a configured number of retries, Docker can then take action, such as restarting the container.

Option 2: Production Deployment with Gunicorn and Nginx

For production environments, it's recommended to use a robust WSGI server like Gunicorn to serve your Flask application, and a reverse proxy like Nginx to handle incoming requests, serve static files, and provide additional security and performance benefits.

Updated Project Structure

For this setup, you'll need a few more files:

my-flask-app/
├── Dockerfile             # For the Flask app with Gunicorn
├── flask-api.py
├── requirements.txt
├── gunicorn_config.py     # Gunicorn configuration (optional but good practice)
├── nginx.conf             # Nginx configuration
└── docker-compose.yml     # Orchestrates both services

Step 2.1: Update requirements.txt

Add gunicorn to your requirements.txt file:

requirements.txt 
Flask
gunicorn

Step 2.2: Create gunicorn_config.py

This file allows you to configure Gunicorn. Create gunicorn_config.py in your project root:

gunicorn_config.py 
# gunicorn_config.py
bind = "0.0.0.0:8000"
workers = 4 # Adjust as needed based on your server's CPU cores (2-4 x CPU cores is a common starting point)
timeout = 120 # Workers silent for more than this many seconds are killed and restarted
keepalive = 5 # The number of seconds to wait for requests on a Keep-Alive connection.

Step 2.3: Create nginx.conf

This configuration tells Nginx to act as a reverse proxy, forwarding requests to your Gunicorn server. Create nginx.conf in your project root:

nginx.conf 
upstream flask_app {
    server web:8000; # 'web' is the service name in docker-compose, 8000 is Gunicorn's port
}

server {
    listen 80; # Nginx listens on port 80 inside the container

    location / {
        proxy_pass http://flask_app;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Optional: Add client_max_body_size if you expect large uploads
        # client_max_body_size 10M;
    }

    # Optional: Serve static files directly via Nginx for better performance
    # For this, you would need to configure Flask to serve static files from a specific path
    # and then map that path in Nginx.
    # For example, if Flask serves static from /app/static:
    # location /static/ {
    #     alias /app/static/;
    # }
}

Step 2.4: Create/Update Dockerfile for Gunicorn

Your Dockerfile will be slightly modified to install Gunicorn and run your Flask app using Gunicorn instead of Flask's development server. Ensure this Dockerfile is in your project root.

Dockerfile 
# Use an official Python runtime as a parent image
FROM python:3.9-slim

# Set the working directory inside the container
WORKDIR /app

# Copy the requirements file into the container at /app
COPY requirements.txt .

# Install any needed packages specified in requirements.txt
RUN pip install --no-cache-dir --trusted-host pypi.python.org -r requirements.txt

# Copy the rest of the application code and Gunicorn config into the container at /app
COPY . .

# Expose Gunicorn's port (default 8000)
EXPOSE 8000

# Command to run your app with Gunicorn
# "flask-api:app" assumes your Flask app instance is named 'app' in flask-api.py
CMD ["gunicorn", "-c", "gunicorn_config.py", "flask-api:app"]

Explanation of the Dockerfile (Option 2 - Gunicorn):

  • FROM python:3.9-slim: Similar to Option 1, this sets the base image to a lightweight Python 3.9 environment.
  • WORKDIR /app: Sets the working directory inside the container to /app.
  • COPY requirements.txt .: Copies the requirements.txt file into the container.
  • RUN pip install --no-cache-dir --trusted-host pypi.python.org -r requirements.txt: Installs all Python dependencies, which now includes Flask and gunicorn.
  • COPY . .: Copies your application code (flask-api.py) and the Gunicorn configuration file (gunicorn_config.py) into the container.
  • EXPOSE 8000: Informs Docker that the container will listen on port 8000. This is the default port Gunicorn will bind to.
  • CMD ["gunicorn", "-c", "gunicorn_config.py", "flask-api:app"]: This command starts the Gunicorn WSGI HTTP server.
    • gunicorn: The Gunicorn executable.
    • -c gunicorn_config.py: Tells Gunicorn to load its configuration from the gunicorn_config.py file.
    • flask-api:app: Specifies how Gunicorn should find your Flask application. It means "look for an application object named app within the Python module flask-api (which corresponds to your flask-api.py file)".

Step 2.5: Create docker-compose.yml

This file defines and runs multi-container Docker applications. It will orchestrate both your Flask app (running with Gunicorn) and Nginx.

docker-compose.yml 
version: '3.8'

services:
  web:
    build: .
    # Use the Dockerfile in the current directory for the 'web' service
    # volumes:
    #   - .:/app # Optional: for live code changes during development (mounts host dir to container)
    expose:
      - "8000" # Expose port 8000 to other services in the Docker network
    environment:
      - FLASK_ENV=production # Set Flask environment

  nginx:
    image: nginx:latest
    ports:
      - "5000:80" # Map host port 5000 to Nginx's port 80
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro # Mount your Nginx config
    depends_on:
      - web # Ensure 'web' service starts before 'nginx'

Explanation of the docker-compose.yml (Option 2):

  • version: '3.8': Specifies the Docker Compose file format version. Using a recent version like '3.8' ensures access to the latest features and syntax.
  • services:: This is the top-level key that defines all the services (containers) that make up your application.
  • web:: Defines a service named web. This service will run your Flask application with Gunicorn.
    • build: .: Instructs Docker Compose to build the Docker image for this service using the Dockerfile located in the current directory (.).
    • expose: - "8000": Exposes port 8000 from the web container to other linked services within the Docker network. This means the nginx service can communicate with the web service on port 8000, but port 8000 is *not* directly accessible from your host machine.
    • environment: - FLASK_ENV=production: Sets an environment variable inside the web container. FLASK_ENV=production is a common practice to configure Flask for a production environment, which might disable debugging features and enable optimizations.
  • nginx:: Defines a service named nginx. This service will run the Nginx reverse proxy.
    • image: nginx:latest: Specifies that Docker Compose should use the latest official Nginx image from Docker Hub for this service.
    • ports: - "5000:80": Maps port 5000 on your host machine to port 80 inside the nginx container. This is how you access your application from your web browser (e.g., http://localhost:5000). Nginx typically listens on port 80 for HTTP traffic.
    • volumes: - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro: Mounts your local nginx.conf file into the nginx container.
      • ./nginx.conf: The path to your Nginx configuration file on your host machine.
      • /etc/nginx/conf.d/default.conf: The destination path inside the Nginx container where Nginx expects to find its main configuration.
      • :ro: Stands for "read-only," meaning the container cannot modify the host file.
    • depends_on: - web: This ensures that the web service (your Flask application) is started and healthy before the nginx service attempts to start. This prevents Nginx from trying to proxy requests to a non-existent backend.

Step 2.6: Build and Run with Docker Compose

Navigate to your my-flask-app directory in the terminal and run:

docker-compose build

Then, to start the services:

docker-compose up -d
  • -d: Runs the containers in detached mode (in the background).

To stop the services:

docker-compose down

Step 2.7: Verification

Your Flask API is now running in a production-like setup! You can access it by opening a web browser and navigating to:

  • API Landing Page: http://localhost:5000/
  • Sample API Request: http://localhost:5000/api?value=10

Nginx is now handling the requests on port 5000 and forwarding them to your Gunicorn-served Flask application.

Option 3: Single Multi-stage Docker Image with Nginx and Gunicorn

This option demonstrates how to create a single, optimized Docker image that includes both your Gunicorn-served Flask application and Nginx as a reverse proxy. This approach leverages multi-stage builds to keep the final image size small and efficient, and provides instructions for pushing it to Docker Hub.

Why Multi-stage Builds?

Multi-stage builds allow you to use multiple FROM statements in your Dockerfile. Each FROM instruction can use a different base image, and each starts a new stage of the build. You can selectively copy artifacts from one stage to another, leaving behind everything you don't need in the final image. This results in a much smaller and more secure production image.

Updated Project Structure

The project structure remains similar to Option 2, but we will only have one Dockerfile that handles everything:

my-flask-app/
├── Dockerfile             # Single multi-stage Dockerfile
├── flask-api.py
├── requirements.txt
├── gunicorn_config.py
├── nginx.conf
└── entrypoint.sh          # Script to start both Gunicorn and Nginx

Step 3.1: Ensure requirements.txt and gunicorn_config.py are in place

These files are the same as described in Option 2. Make sure they are present in your project root.

requirements.txt 
Flask
gunicorn
gunicorn_config.py 
# gunicorn_config.py
bind = "0.0.0.0:8000"
workers = 4
timeout = 120
keepalive = 5

Step 3.2: Ensure nginx.conf is in place

This file is also the same as described in Option 2. It configures Nginx to proxy requests to Gunicorn.

nginx.conf 
upstream flask_app {
    server 127.0.0.1:8000; # Gunicorn will run on localhost within the same container
}

server {
    listen 80;

    location / {
        proxy_pass http://flask_app;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Step 3.3: Create entrypoint.sh

Since we're running both Gunicorn and Nginx in a single container, we need a script to start both processes. Create entrypoint.sh in your project root:

entrypoint.sh 
#!/bin/sh
# Start Gunicorn in the background
gunicorn -c gunicorn_config.py flask-api:app &

# Start Nginx in the foreground
nginx -g "daemon off;"

# Wait for any process to exit
wait -n

# Exit with status of process that exited first
exit $?

Explanation of the entrypoint.sh script (Option 3):

  • #!/bin/sh: This is the "shebang" line, which tells the operating system to execute the script using the /bin/sh interpreter.
  • gunicorn -c gunicorn_config.py flask-api:app &: This command starts the Gunicorn server.
    • gunicorn -c gunicorn_config.py flask-api:app: Configures and starts Gunicorn to serve your Flask application.
    • &: This crucial symbol runs the Gunicorn process in the background. This allows the script to continue to the next command (starting Nginx) without waiting for Gunicorn to finish.
  • nginx -g "daemon off;": This command starts the Nginx web server.
    • nginx: The Nginx executable.
    • -g "daemon off;": This tells Nginx to run in the foreground. In Docker, the main process of the container must run in the foreground. If Nginx were to daemonize (run in the background), Docker would think the container's main process has exited and would stop the container.
  • wait -n: This command waits for any background job to complete. In this script, it specifically waits for the Gunicorn process (which was started with &) to exit. If Gunicorn crashes, wait -n will detect it, and the script will proceed to the next line.
  • exit $?: This command exits the script with the exit status of the last executed command (or the command that wait -n reported). This is important because it propagates the exit status of either Gunicorn or Nginx to the Docker container. If one of them fails, the container will exit with a non-zero status, indicating an error to Docker.

Step 3.4: Create the Multi-stage Dockerfile

This Dockerfile will build your Python application in one stage and then combine it with Nginx in a final, lean image.

Dockerfile 
# --- Stage 1: Build Python Application with Gunicorn ---
FROM python:3.9-slim AS python-builder

WORKDIR /app

# Copy requirements and install Python dependencies
COPY requirements.txt .
RUN pip install --no-cache-dir --trusted-host pypi.python.org -r requirements.txt

# Copy the application code and Gunicorn config
COPY . .

# --- Final Stage: Combine Nginx and Gunicorn ---
FROM nginx:stable-alpine

# Remove default Nginx config
RUN rm /etc/nginx/conf.d/default.conf

# Copy Nginx config from the build context
COPY nginx.conf /etc/nginx/conf.d/default.conf

# Copy Python application from python-builder stage
# This includes the installed packages and your application code
COPY --from=python-builder /usr/local/bin/gunicorn /usr/local/bin/gunicorn
COPY --from=python-builder /usr/local/lib/python3.9/site-packages /usr/local/lib/python3.9/site-packages
COPY --from=python-builder /app /app

WORKDIR /app

# Expose Nginx's default HTTP port
EXPOSE 80

# Copy and set permissions for the entrypoint script
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

# Use the entrypoint script to start both services
ENTRYPOINT ["/entrypoint.sh"]

Explanation of the Multi-stage Dockerfile (Option 3):

This Dockerfile uses a multi-stage build process to create a single, optimized image containing both your Flask application (served by Gunicorn) and Nginx.

Stage 1: python-builder

  • FROM python:3.9-slim AS python-builder: This defines the first build stage, named python-builder. It uses a lightweight Python 3.9 image as its base. This stage is responsible for building your Python application and installing its dependencies.
  • WORKDIR /app: Sets the working directory inside this stage to /app.
  • COPY requirements.txt .: Copies your requirements.txt file into the /app directory of this stage.
  • RUN pip install --no-cache-dir --trusted-host pypi.python.org -r requirements.txt: Installs all Python dependencies (Flask and Gunicorn) into this stage.
  • COPY . .: Copies your Flask application code (flask-api.py) and Gunicorn configuration (gunicorn_config.py) into this stage.

Final Stage: Combining Nginx and Gunicorn

  • FROM nginx:stable-alpine: This defines the final build stage. It uses a lightweight Nginx image based on Alpine Linux as its base. This stage will contain the final production image.
  • RUN rm /etc/nginx/conf.d/default.conf: Removes the default Nginx configuration file provided by the base image, as we will be providing our own.
  • COPY nginx.conf /etc/nginx/conf.d/default.conf: Copies your custom nginx.conf file from your local project directory (the build context) into the Nginx configuration directory inside the container.
  • COPY --from=python-builder /usr/local/bin/gunicorn /usr/local/bin/gunicorn: This is a key part of multi-stage builds. It copies the Gunicorn executable from the python-builder stage into the final Nginx stage.
  • COPY --from=python-builder /usr/local/lib/python3.9/site-packages /usr/local/lib/python3.9/site-packages: Copies all the Python packages (including Flask) that were installed in the python-builder stage into the final image.
  • COPY --from=python-builder /app /app: Copies your application code (flask-api.py) and Gunicorn configuration (gunicorn_config.py) from the python-builder stage into the final image.
  • WORKDIR /app: Sets the working directory for the final image to /app.
  • EXPOSE 80: Informs Docker that the container will listen on port 80, which is Nginx's default HTTP port.
  • COPY entrypoint.sh /entrypoint.sh: Copies your custom entrypoint.sh script into the root of the container.
  • RUN chmod +x /entrypoint.sh: Makes the entrypoint.sh script executable.
  • ENTRYPOINT ["/entrypoint.sh"]: Specifies that the entrypoint.sh script will be executed when the container starts. This script is responsible for starting both Gunicorn and Nginx.

Step 3.5: Build the Multi-stage Docker Image

Navigate to your my-flask-app directory in the terminal and run the following command to build your single, optimized image:

docker build -t your_dockerhub_username/my-flask-app-prod:latest .

Replace your_dockerhub_username with your actual Docker Hub username.

Step 3.6: Run the Multi-stage Container

You can now run your combined application container:

docker run -d -p 5000:80 your_dockerhub_username/my-flask-app-prod:latest
  • -d: Runs the container in detached mode.
  • -p 5000:80: Maps host port 5000 to Nginx's port 80 inside the container.

Step 3.7: Push to Docker Hub

To share your image or deploy it to other environments, you can push it to Docker Hub:

  1. Log in to Docker Hub: 
    docker login

    You will be prompted for your Docker Hub username and password.

  2. Push the image: 
    docker push your_dockerhub_username/my-flask-app-prod:latest

Once pushed, your image will be available on Docker Hub, and you can pull and run it on any machine with Docker installed.

Step 3.8: Verification

Your Flask API is now running in a single, optimized Docker container, served by Nginx and Gunicorn. You can access it by opening a web browser and navigating to:

  • API Landing Page: http://localhost:5000/
  • Sample API Request: http://localhost:5000/api?value=10
