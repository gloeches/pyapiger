Proposal: Gunicorn-based Web Server for Agent Environment

Overview

This script serves as the primary entry point for launching the web arena agent environment. It configures and starts a web server using Gunicorn to host the agent's application. The server is designed to be accessible via a specified host and port, enabling interaction with the agent. The script initializes and runs a web server for the agent environment. It utilizes argparse to define command-line arguments for server configuration, specifically --port, --host, and --workers.

Core Component: Custom Gunicorn Application

To programmatically control the Gunicorn server from within our script, a custom application class, CustomGunicornApp, is defined. This class integrates our Flask application (imported from .server) with Gunicorn by inheriting from gunicorn.app.base.BaseApplication and customizing its configuration and application loading mechanisms.

Code Implementation

class CustomGunicornApp(BaseApplication):
    def __init__(self, app, options=None):
        self.options = options or {}
        self.application = app
        super().__init__()

    def load_config(self):
        for key, value in self.options.items():
            if key in self.cfg.settings and value is not None:
                self.cfg.set(key.lower(), value)

    def load(self):
        return self.application

Code Explanation

The CustomGunicornApp class acts as a bridge, allowing our Python script to configure and run a Gunicorn server instance.

  • __init__(self, app, options=None): The constructor method initializes the application.
    • app: This is the web application instance (e.g., a Flask app) that Gunicorn will serve.
    • options: A dictionary containing Gunicorn configuration settings, such as bind (host and port), workers (number of processes), or timeout.
  • load_config(self): This method is overridden from Gunicorn's BaseApplication. It iterates through the options dictionary provided during initialization and applies each valid setting to Gunicorn's internal configuration object (self.cfg). This is the key to programmatically configuring Gunicorn.
  • load(self): This method is also required by Gunicorn. It's responsible for returning the actual web application instance that Gunicorn will run. Here, it simply returns the app that was passed into the constructor.

Launch Sequence

The main launch function will parse command-line arguments, assemble the Gunicorn options dictionary (including the binding address, worker count, and timeout), and then start the server. This is achieved by creating an instance of CustomGunicornApp with the Flask app and the configured options, and then calling its run() method.

Recommended Docker Implementation

To containerize this application effectively, it's important to handle process signals (like SIGTERM from docker stop) correctly for graceful shutdowns. A common Docker warning arises when using the "shell form" of the CMD instruction, as it can prevent these signals from reaching the application.

The recommended approach is to centralize the application's startup logic within an entrypoint.sh script. This ensures that gunicorn runs as the main process (PID 1) inside the container and receives signals directly.

1. The `entrypoint.sh` Script

This script becomes responsible for starting the Gunicorn server. It reads the API_PORT environment variable to configure the port dynamically. 

#!/bin/sh
# entrypoint.sh

# Default to port 8000 if API_PORT is not set or empty
PORT=${API_PORT:-8000}

# Use exec to replace the shell process with gunicorn.
# This makes gunicorn the main process, allowing it to receive signals directly.
echo "Starting gunicorn on port $PORT"
exec gunicorn flask-api:app -b 0.0.0.0:$PORT
  • PORT=\${API_PORT:-8000}: This line safely reads the API_PORT environment variable. If the variable is not set or is empty, it defaults to 8000.
  • exec gunicorn...: The exec command replaces the current shell process with the gunicorn process. This is crucial for proper signal handling, as it avoids leaving a shell process to intercept signals from Docker.

2. The `Dockerfilegunicorn`

The Dockerfile sets up the environment, copies the files, and designates entrypoint.sh as the startup command. The CMD instruction is no longer needed, as the entrypoint now handles the entire command. 

# Use an official Python runtime as a parent image
FROM python:3.13-slim

WORKDIR /app

# Set the environment variable for the API port
ENV API_PORT=8000

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Make the entrypoint script executable
RUN chmod +x entrypoint.sh

# Expose the port defined by the environment variable
EXPOSE 8000

# Set the entrypoint to run our script.
# This uses the "exec form" which is the recommended practice.
ENTRYPOINT ["./entrypoint.sh"]

# CMD is no longer needed as the entrypoint handles execution
  • ENV API_PORT=8000: Sets the default port as an environment variable in the container. This can be easily overridden at runtime (e.g., docker run -e API_PORT=5000 ...).
  • ENTRYPOINT ["./entrypoint.sh"]: This uses the "exec form" of ENTRYPOINT. It directly runs the script, which is the recommended practice for ensuring correct signal handling.
